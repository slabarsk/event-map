Event Map Architecture

System architecture, repo layout, data model and the three core flows of the app that collects İzmir events every day and pins them on a map. Everything here follows the decisions in the roadmap; nothing outside its scope.

Section 1

System architecture

The crawler runs as a separate Python worker on GitHub Actions, because Playwright cannot run inside Supabase Edge Functions (Deno). The app reaches Supabase only through RLS-protected reads and Edge Functions.

data flow Claude call inside Supabase

Fetch order

For each source the worker tries an official API or RSS first, then Firecrawl, and Playwright only when the site needs a browser.

Query-to-SQL

Claude never writes raw SQL. It returns a JSON filter, the filter is validated, and the parameterized events_near RPC runs it.

Privacy

The user's location is used for the query and not stored. Account deletion goes through delete-account.

Section 4

Core flows

The three flows behind Demo Day scope a), b) and c).

a) Daily crawl

If the content has not changed, Claude is never called. A missing price is looked up first and estimated only if the lookup fails.

      W->>M: venue address
      M-->>W: coordinates
      W->>DB: candidate pairs (ST_DWithin, ±2 h, pg_trgm)
      opt ambiguous pair
        W->>C: same event?
        C-->>W: yes / no
      end
      W->>DB: upsert events + event_sources
    end
  end
  W->>DB: write crawl_runs (counts, errors, tokens)

b) "Free concerts near me tonight"

Claude turns the question into a filter made only of allowed fields. The SQL is always the same parameterized function.

  C-->>F: JSON filter: category=concert, max_price=0, time_window=tonight, radius_m=5000

  F->>DB: events_near(lat, lng, 5000, now, end of night, concert, 0)
  DB-->>F: events sorted by distance
  F-->>A: results + applied filters
  A-->>U: filtered pins on the map

c) Instagram share → pin

Instagram is never scraped. The user shares the post, Claude drafts the event, and no pin is created until the user confirms.
